## 2026-08-02 — `njt_client.py`: assumed token TTL was never checked against the real 10/day quota, fixed 25min → 6h
**Agent**: data-engineer-agent
**Did**: changed `njt_client.py`'s assumed token TTL (previously a `25 * 60` magic number inline in `_fetch_token`) to a new named constant, `TOKEN_ASSUMED_TTL_SECONDS = 6 * 60 * 60` (6 hours), with the quota arithmetic spelled out explicitly in a code comment above it. The DB-backed `NjtTokenCache` cache added earlier this session (see the 2026-08-02 "Track-assignment logging + NJT getToken quota discovery" entry above) was not touched -- `_ensure_token`/`_load_cached_token`/`_save_cached_token` all consume `expires_at` exactly as before, just computed from the new constant instead of the old one, so the persistence logic flows through correctly without any changes to it.
**Issue**: the 25-minute assumed TTL, still in place after this session's DB-cache fix, was never actually checked against the real 10/day `getToken` quota discovered earlier the same session -- it predates that discovery entirely (picked as "a conservative assumption" before anyone knew the quota existed).
**Root cause**: 24h / 10 tokens = 2.4h is the theoretical max sustainable refresh interval if every single daily quota unit went to token refresh alone. A 25-minute TTL implies a refresh roughly every 25 minutes regardless of how well the DB cache shares that token across processes (the cache only prevents *redundant* refreshes within a still-valid window -- it does nothing to lengthen how long that window is) -- ~57 real `getToken` calls/day, nearly 6x the actual 10/day quota. The DB-backed cache fixed the *cross-process-doesn't-share-a-token* bug, but would still have burned through the daily quota by itself well before a single day was over, just more slowly than the fully-uncached version.
**Fix**: `TOKEN_ASSUMED_TTL_SECONDS` set to 6 hours (~4 refreshes/day out of 10 available), landing meaningfully under the 2.4h theoretical ceiling rather than cutting it as close as mathematically possible -- leaves real margin for manual `workflow_dispatch` runs, local dev/testing, and the fact this project now has three NJT-authenticated scripts (`poll_gtfs_rt.py`, `poll_alerts.py`, `poll_track_assignments.py`, the last not yet wired into `/infra`'s workflow) that could each independently trigger a refresh if the persistent cache ever misses (DB unreachable, etc.), not just one script as when 25 minutes was first chosen. The comment in `njt_client.py` documents plainly that 6 hours is still a guess, not an empirically confirmed server-side TTL -- NJT doesn't publish one -- just a far safer guess sized against the known quota instead of picked arbitrarily; if tokens are ever found to expire before this window in practice, that would surface as real `getToken`/authentication errors in the scheduled workflow's logs, which is the correct signal to shorten this constant, not a guess made in a vacuum.
**Verified**: no live API call was made (today's quota is exhausted from earlier testing) -- verification was via code reading (confirmed `_ensure_token`'s cache-read/cache-write logic is unchanged and just consumes the new `expires_at` value the same way it consumed the old one) and `python -m py_compile njt_client.py`, both clean.
**Lesson**: a "conservative assumption" made before a real constraint is known can become the opposite of conservative once that constraint is discovered -- worth re-checking any pre-existing guessed constant against a newly-discovered hard limit rather than assuming a fix elsewhere in the same code path (here, the DB cache) fully addresses the underlying problem. The cache and the TTL were two separate bugs against the same quota; fixing only one (the cache, in this session's earlier work) still left the other quietly burning ~6x the real daily budget.

## 2026-08-02 — ML: per-train NY Penn track prediction (Clever Commute-style), zero rows on real data as expected
**Agent**: ml-engineer-agent
**Did**: built `ml/compute_track_predictions.py`, a new precomputation script (same pattern as `compute_baseline.py`: query accumulated history, honest sample-size gating, write to a dedicated output table rather than computing live per request). Predicts which physical track a *specific train* will use at New York Penn Station, styled after Clever Commute's own published methodology rather than guessed at: groups `ingestion`'s `track_assignments` by exact `train_id` (not line/hour-of-day, which is far too coarse for "which of ~20 physical tracks"), filtering `track IS NOT NULL` first — a null track means "unknown," never "the train used no track," so it's excluded before grouping rather than counted as evidence for or against anything. For each train with enough real observations, computes the most common track, its share of that train's total observations, and a confidence tier: **high** = share ≥70% AND sample ≥10; **medium** = share ≥40% AND sample ≥5; **low** = sample ≥3 (any share); below sample 3, no row is written at all (matches `train_model.py`'s established honesty convention of skipping rather than fabricating a low-confidence prediction). Added `TrackPrediction` (new output table, `train_id` primary key, plus `station_code`/`predicted_track`/`confidence`/`sample_size`/`top_track_share`/`computed_at`) and a read-side `TrackAssignment` mirror to `ml/models.py`, and the tier thresholds (`TRACK_MIN_SAMPLES_LOW/MEDIUM/HIGH`, `TRACK_SHARE_MEDIUM/HIGH`, `NY_PENN_STATION_CODE`) to `ml/config.py`. Safely re-runnable (upsert on `train_id`, same as `compute_baseline.py`'s upsert on its own key).
**Verified**: two-part, exactly as the task called for. (1) **Synthetic**: seeded `TrackAssignment` rows for six synthetic `train_id`s directly into the real Postgres connection inside a transaction that was rolled back, never committed — confirmed all three confidence tiers compute correctly (10 obs/80% share → high; 6 obs/50% share → medium; 3 obs/33% share → low), confirmed a below-3-sample train and an all-null-track train both correctly produce zero rows, and confirmed a train with 3 real + 5 null observations correctly reports `sample_size=3` (the nulls don't inflate the denominator) and correctly caps at "low" (not "high") because sample size, not just share, gates the higher tiers. ## 2026-08-01 — PRD-v2 Phase 1: feed-anomaly reconciliation (data-confidence indicator groundwork)
**Agent**: data-engineer-agent
**Did**: built the `/ingestion` half of PRD-v2 Phase 1's "data-confidence indicator" -- the feature meant to turn NJT's own most-cited weakness (riders don't trust its real-time data: vehicles vanish from tracking, schedules show already-departed trains) into this project's differentiator, by honestly flagging when the underlying feed itself looks unreliable. Added a new additive `feed_anomalies` table (`id`, `trip_id`, `line`, `anomaly_type`, `detected_at`, `detail`) to `models.py` -- same pattern as `service_alerts`/`delay_baseline`, no changes to `trip_updates`' existing schema/consumers. New `reconcile_anomalies.py` runs inside every `poll_gtfs_rt.py` invocation, using the *same DB session*, called *before* that poll's own `trip_updates` insert (so "the previous poll" in the comparison means the actual previous poll, not the one about to be written) -- necessary because each poll is a stateless script invocation with no in-process memory; all "was this trip active last cycle" state has to come from querying what prior polls already committed to Postgres. Two detectors: (1) `vanished_mid_route` -- a trip present on the previous poll whose own next-stop ETA (`actual_time` = `scheduled_time` + delay) hadn't passed yet, that's then completely absent from this poll's live response; guarded by a 20-minute max gap between polls (a multi-hour gap, e.g. from a CI outage, makes the comparison meaningless) and a 1-minute grace period (a trip whose ETA was seconds away plausibly just finished that leg). Also synthetically confirmed the vanished-trip detector's negative case explicitly (the task's own verification bar): a trip whose next-stop ETA had already passed *before* the poll that last saw it (a plausible ordinary completion) is correctly NOT flagged when it disappears, while a trip still clearly short of its ETA is correctly flagged when it disappears at the same moment -- and confirmed the 20-minute gap guard suppresses detection entirely when the previous poll is too old a reference point.
