# /backend

Owned by `backend-engineer-agent`. FastAPI app serving live status, predictions, and scorecards, reading from Postgres (populated by `/ingestion`) and precomputed predictions (populated by `/ml`).

## Status (Week 5 + PRD-v2 Phase 1: advisory, live board, on-this-train companion view) — full endpoint set built and verified against real data
- `GET /health` — liveness check.
- `GET /lines` — list of in-scope Newark-area lines.
- `GET /lines/{line}/live` — most recent trip_updates reading per trip, within a 30-minute window.
- `GET /lines/{line}/predict` — prefers a v2 LightGBM prediction (`ml_predictions`) over the v1 statistical baseline (`delay_baseline`) when both exist for the current hour/day-of-week, since `/ml` only ever writes a v2 bucket after it's beaten the baseline on held-out data. Falls back to the baseline, then to an honest `{"status": "insufficient_data", ...}` rather than a fabricated number. The response includes `"source": "ml_model" | "statistical_baseline"` so callers know which one they got. The shared preference-order logic lives in `routers/lines.py`'s `get_current_risk()`, reused by `/advisory` below.
- `GET /lines/{line}/scorecard` — rolling 7/30-day on-time %, deduplicated to one reading per (trip, calendar day) so a trip re-polled every 5 minutes doesn't get counted repeatedly. Always includes `sample_size` so the frontend can hedge on a small sample.
- `GET /alerts?line=` — active service alerts, optionally filtered by line.
- `GET /lines/{line}/advisory` — weather-aware proactive commute advisory (`routers/advisories.py`, PRD-v2 Phase 1). Looks at `weather_hourly` rows in the next 6 hours for adverse conditions (precipitation probability >= 60%, wind >= 25mph, or a snow/ice/thunderstorm keyword in the forecast text — see the module docstring for the reasoning behind each threshold) and cross-references that against `get_current_risk()`. Only returns a human-readable advisory message (`status: "ok"`) when both an adverse-weather hour AND a "medium"/"high" risk level are present; otherwise returns `"no_advisory"` (conditions are unremarkable) or `"insufficient_data"` (no baseline/ml prediction exists yet) rather than inventing urgency.
- `GET /stations` — distinct station names currently seeing Newark-area-line traffic within the live window, derived from recent `trip_updates` rows (NOT the full static `stops` table — see `routers/stations.py`'s module docstring for why: no reliable join key exists between the live feed's station-name `stop_id` and static GTFS's numeric one, and the static table's ~231 stations mostly aren't Newark-area-relevant anyway).
- `GET /stations/{station_name}/board` — station-grouped "live board" (PRD-v2 Phase 1's DepartureVision-style board data source): every upcoming departure across all Newark-area lines at that station within the live window, sorted by `scheduled_time` ascending, each with `line`, `direction`, `scheduled_time`, `delay_seconds`, and a derived `status` (`on_time`/`delayed`/`unknown`, same 60s threshold as `/scorecard`). `station_name` matches `trip_updates.stop_id` case-insensitively; URL-encode station names with spaces. Returns `200` with an empty `departures` list (never `404`) for an unrecognized-or-currently-quiet name, since there's no fixed station enumeration to validate against — same honesty convention as `/predict`'s `insufficient_data`.
- `GET /trips/{trip_id}/upcoming-stops` — "on this train" companion view (PRD-v2 Phase 1): ordered list of a live trip's remaining stops with station names and estimated arrivals. **`trip_id` is not the same identifier space as static GTFS's `Trip.trip_id`** — empirically verified (see `ENGINEERING_LOG.md`'s 2026-08-01 "on this train" entry and `models.py`'s `Trip` docstring): 17 of 69 sampled live trip_ids coincidentally also existed as a static trip_id, but 0 of those matches agreed on line/route, confirming it's ID-space collision, not a real join key. Uses schedule-proximity matching instead (`routers/trips.py`): resolves the live trip's route via `Route.short_name`, filters static `Trip` candidates by direction (`direction_id` "0"/"1" empirically mapped to the live feed's "Eastbound"/"Westbound"), and picks whichever candidate's first scheduled stop is closest in time-of-day to the live trip's own `scheduled_time`. Every response is labeled `"match_type": "schedule_proximity"` with a `match_time_gap_minutes` field so callers can judge match quality — never presented as an exact join. Each stop's `estimated_arrival` is the matched trip's static schedule with the live trip's current `delay_seconds` applied as a uniform offset (not a per-stop live reading — the feed only reports one current position per trip). 404s if `trip_id` has no `trip_updates` row at all.
- `GET /trips/{trip_id}/quiet-commute` — best-effort Quiet Commute car lookup (PRD-v2 Phase 1, `routers/trips.py`). **Deliberately not a lookup against a specific train number**: NJ Transit's press materials describe the program as expanded to NEC peak-hour trains into Newark/NY Penn but publish no machine-readable per-train list, and this project has already confirmed (same finding as `/upcoming-stops` above) that neither the live feed's `trip_id` nor static GTFS's `trip_id` maps to any verifiable public train-number scheme — so this endpoint doesn't attempt that join at all. Instead it applies a rule to only the signals this project can verify from the live `trip_updates` row: line must be `NEC`, trip must be scheduled on a weekday, and scheduled time/direction must fall in a peak window — AM 6:00–10:00 local inbound (`direction: "Eastbound"`, toward Newark/NY Penn) or PM 16:00–20:00 local outbound (`"Westbound"`, away from Newark/NY Penn). The Eastbound/Westbound → inbound/outbound mapping reuses the same empirically-verified correspondence `/upcoming-stops` already established against static GTFS's `direction_id`/`trip_headsign`, rather than re-deriving it via a fresh (and known-unreliable) `trip_id` join to the static `Trip` table. If direction can't be determined, falls back to time-of-day only and says so in `reasoning`. Response: `{"trip_id", "line", "direction", "scheduled_time", "likely_quiet_commute": bool, "confidence": "best_effort", "reasoning": "<why>", "disclaimer": "<rider-facing caveat, always present>"}`. 404s under the same condition as `/upcoming-stops` (no `trip_updates` row at all for the given `trip_id`).
- `GET /stations/static?q=<name>` — statewide station-name search (added `i-am-not-happy-pure-aurora` plan step 5, `routers/stations.py`): case-insensitive partial match (`ILIKE '%q%'`) over the full static `stops` table (231 rows, no line filter), returning up to `STATION_SEARCH_LIMIT` (20) `{stop_id, stop_name}` pairs, ordered by `stop_name`. This is the lookup that resolves an arbitrary station name to the numeric `stop_id` `/stations/{stop_id}/transfers` needs — that endpoint's identifier space has no other statewide discovery path (see `routers/stations.py`'s module docstring). An empty `q` or a query with zero matches both return `200` with an empty `stations` list, never a `404` — same honesty convention as `/stations/{name}/board`'s empty-departures case.
- `GET /stations/{stop_id}/transfers` — transfer-aware hub view (PRD-v2 Phase 1, widened statewide in plan step 5, `routers/stations.py`): for any real station, which lines actually call there and each one's next few *scheduled* (static-timetable) departures. `stop_id` is the static GTFS numeric stop_id (e.g. `107` for Newark Penn Station), not the live-feed station-name string `/stations`/`/stations/{name}/board` use. Existence is checked against the real statewide `stops` table (`db.get(Stop, stop_id)`) rather than a hardcoded two-station allowlist — any real `stop_id` works now, not just the original two Newark hubs; a 404 (with a pointer to `/stations/static`) is returned only for a genuinely unknown `stop_id`. Built entirely from the static schedule (`StopTime` → `Trip` → `Route`, deduped by `(time, headsign)` since no `calendar.txt` is loaded to distinguish weekday/weekend service_id variants) — the live feed's trip_id has no reliable join to static `Trip.trip_id` either (same mismatch as `/trips/{trip_id}/upcoming-stops` above), so no live delay data is blended in for other lines. The route join is no longer filtered by `RAIL_LINES` — it returns whichever real routes (including light rail, if the stop happens to be a light-rail stop) actually have `StopTime` rows at that `stop_id`, since the search/lookup endpoints above are deliberately unfiltered by line too. Every response carries `"source": "static_schedule"` plus an explicit `note` field, never presented as live.
- `GET /lines/{line}/data-confidence` — data-confidence indicator (PRD-v2 Phase 1, `routers/data_confidence.py`): reads `feed_anomalies` (written by `/ingestion`'s `reconcile_anomalies.py`, run inside every `poll_gtfs_rt.py` cycle) to report whether the live feed has looked reliable for this line in the last 3 hours (`ANOMALY_WINDOW_HOURS` — long enough to span dozens of poll cycles at the current 5-min polling interval without over/under-weighting one transient reading, short enough to reflect current behavior rather than diluting today's status with an already-resolved issue from hours ago). Three `status` values, deliberately kept distinct rather than collapsed into one score: `"unknown"` (no `trip_updates` row for this line within the same freshness window `/live` uses — there's no recent polling to evaluate at all, e.g. during an ingestion outage; reporting "ok" here would itself be a fabricated-confidence bug), `"ok"` (recent polling exists, zero anomalies in the window), `"issues_detected"` (recent polling exists, >=1 anomaly — `anomaly_counts` by type plus up to 5 `recent_anomalies` with `trip_id`/`detected_at`/`detail` so callers get something concrete, not a vague trust score). No new scheduled/cached-compute job — this is a cheap indexed read (`line`, `detected_at`) same as `/alerts`, consistent with the rest of this API's pattern of only precomputing genuinely expensive work (ML predictions, baselines).

Verified against real production data (not just a throwaway test DB): all endpoints except `/advisory`'s "ok" branch tested live against Postgres after NJ Transit RailData access was approved 2026-08-01 — see `ENGINEERING_LOG.md`. `/advisory`'s weather-detection logic was checked against real `weather_hourly` rows, but its "ok" branch (adverse weather + elevated risk) is currently only logic-verified against seeded synthetic data, because `delay_baseline` is empty in production right now (no rows for any line/hour/day-of-week bucket yet) — see the 2026-08-01 advisory endpoint entry in `ENGINEERING_LOG.md` for the full honesty accounting. `/stations` and `/stations/{station_name}/board` were verified against real `trip_updates` rows too, though at verification time the actual 30-minute live window was empty (last real ingestion poll was ~7h stale in this environment) — see the `ENGINEERING_LOG.md` entry for how that was worked around for verification without changing the shipped window. `/trips/{trip_id}/upcoming-stops` was verified the same way (against stale-but-real rows, since `trip_id` lookup doesn't depend on the live window): real trip `7821` (NEC, Westbound) matched to a static trip whose stop order — NY Penn → Secaucus Upper Level → Newark Penn → Newark Airport → Rahway → Metropark → Metuchen → Edison → New Brunswick → Jersey Ave. → Princeton Jct. → Hamilton → Trenton Transit Center — is exactly correct real NEC geography for a NY-to-Trenton run, with a 3.8-minute match gap; trip `6912` (MNE, Eastbound) similarly matched a static trip with correct real M&E geography (Lake Hopatcong through to Hoboken) and a 9.0-minute gap. The 42s/94s known current delays applied correctly as uniform offsets to every stop's `estimated_arrival`. `/stations/{stop_id}/transfers` was verified live for both real hub stop_ids: `106` (Newark Broad Street) resolved to `{BNTN, BNTNM, MNE, MNEG}` (Montclair-Boonton + Morris & Essex + Gladstone) and `107` (Newark Penn Station) resolved to `{NEC, NJCL, NJCLL, RARV}` (Northeast Corridor + North Jersey Coast + Raritan Valley) — two non-overlapping, real-world-correct line sets (neither zero nor identical), plus a real 404 for an unscoped stop_id (`999`). **Re-verified 2026-08-02 after the statewide widening** (`i-am-not-happy-pure-aurora` plan step 5): `stop_id` `10` (Atlantic City, real `ATLC` schedule, 45 distinct scheduled times), `stop_id` `100` (Nanuet, real `PASC` schedule) and the original `106`/`107` all resolved correctly (the old two hubs are an unchanged subset, not a regression); `999999` (never a real static `stop_id`) still 404s cleanly with a message now pointing callers at the new search endpoint instead of the old two-station allowlist. `GET /stations/static` was verified against real `stops` rows for three cases: `q=newark` (4 real matches, including the two old hubs plus Newark Airport and a light-rail station), `q=avenue` (13 real matches), and `q=zzzzznotastation` (0 matches, honest empty list, `200` not `404`). All of the above were run twice — once via `TestClient` in-process against the real production Supabase Postgres (bypassing local networking entirely) and once as real HTTP round-trips against a freshly-started local `uvicorn` instance on port 8010 — because the project's existing port-8001 dev server was found to have the same "unkillable zombie TCP listener" issue previously documented for port 8000 (a stale kernel-level socket entry with no owning process — confirmed via `wmic process` returning no instance for the listening PID — silently serving the pre-edit code on every request); see `ENGINEERING_LOG.md` for the full note. After-midnight "next departure" handling was both unit-checked directly (`24:19:00`/`25:41:00`-style raw GTFS strings, plus a synthetic 23:50→00:19 wraparound case) and confirmed against real after-midnight rows that exist in production at stop_id `106` (e.g. `24:19:00`, `25:41:00`), which correctly computed as ~530-612 minutes away from the real verification-time now rather than a negative or wrapped-wrong value. `/lines/{line}/data-confidence`'s `"unknown"` branch is real-data-verified: `feed_anomalies` is genuinely empty in production right now (0 rows — expected, see the 2026-08-01 data-confidence entry in `ENGINEERING_LOG.md` for why: NJT's RailData auth endpoint has been returning 500s this session, so live ingestion hasn't run) and the last real `trip_updates` poll for `NEC` was ~7.5h stale at verification time, correctly producing `"unknown"` rather than a false "ok". The `"ok"` and `"issues_detected"` branches are synthetic-verified only (feed_anomalies had nothing real to exercise them against): a temporary DB transaction inserted a fresh `trip_updates` row plus two in-window/one out-of-window `feed_anomalies` rows, confirmed the response counted only the two in-window anomalies correctly by type, confirmed a second unrelated line (`MNE`) was unaffected, then rolled back with nothing committed to production. `/trips/{trip_id}/quiet-commute` was verified against all 69 distinct real trip_ids sampled from production (`NEC`, `NJCL`, `MNE`, `MNEG`, `BNTN`, `RARV`) via HTTP against a locally-running instance plus a direct pure-function sweep: every non-`NEC` trip correctly returned `false` with a line-specific reason; every real `NEC` trip in the sample happened to be scheduled either late Friday evening or in the very early hours of Saturday (last real ingestion poll at verification time), so all correctly returned `false` too — either for falling outside both peak windows or for landing on a weekend, exercising both `NEC`-specific rejection branches against genuine data. Because no real sampled row fell in a true weekday-peak window, the `true` branches (both directions, both AM/PM windows) and the unknown-direction fallback were additionally verified with hand-constructed weekday/weekend and boundary-time cases (e.g. `05:59` vs. exactly `06:00`, `19:59` vs. exactly `20:00`) run through the same production code path, confirming correct inclusive/exclusive window edges and direction-mismatch rejection (e.g. an `Eastbound` NEC trip during the PM window correctly returns `false`, not `true`).

## Setup
```
python -m venv .venv
.venv/Scripts/activate      # .venv/bin/activate on Mac/Linux
pip install -r requirements-dev.txt   # includes test deps
cp .env.example .env         # fill in DATABASE_URL (same Supabase DB as /ingestion)
```

## Run locally
```
uvicorn main:app --reload
```
Then visit http://localhost:8000/docs for interactive API docs (FastAPI auto-generates this).

## Notes
- `models.py` is a deliberate read-side mirror of `/ingestion/models.py`, not a shared import — see the docstring in that file for why (agent ownership boundaries per `AGENTS.md`). If the DB schema changes, update both.
- **Deferred, not forgotten**: a per-trip `has_recent_anomaly: bool` field on `GET /lines/{line}/live` (so the dashboard could eventually highlight a specific flaky-looking trip) was considered alongside `/lines/{line}/data-confidence` and deliberately left out of that pass. Reasoning: it would add a join/extra field to an endpoint the frontend already depends on for no current consumer (no UI surfaces it yet — frontend work here is explicitly a separate follow-up per PRD-v2 Phase 1), and `feed_anomalies` is empty in production right now anyway (ingestion outage), so there's nothing real to show today. If/when `frontend-engineer-agent` wants to surface this, the cleanest addition is a `WHERE trip_id IN (...) AND detected_at >= <window>` lookup against `feed_anomalies` joined onto `/live`'s existing trip list — flag this as a response-shape change to brief the frontend on before shipping it.
